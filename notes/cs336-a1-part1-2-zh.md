## 2 字节对编码（BPE）分词器

在作业的第一部分，我们将训练并实现一个**字节级**字节对编码（BPE）分词器 [R. Sennrich et al., 2016; C. Wang et al., 2019]。具体而言，我们会把任意（Unicode）字符串表示为字节序列，并在这个字节序列上训练 BPE 分词器。之后，我们会用该分词器把文本（字符串）编码为 token（整数序列），用于语言建模。

### 2.1 Unicode 标准

Unicode 是一种文本编码标准，它把字符映射为整数**码点**（code point）。截至 Unicode 17.0（2025 年 9 月发布），该标准在 172 种文字中定义了 159,801 个字符。例如，字符 "s" 的码点是 115（通常记作 U+0073，其中 U+ 是约定前缀，0073 是 115 的十六进制写法）；字符 "牛" 的码点是 29275。在 Python 中，你可以用 `ord()` 函数把单个 Unicode 字符转换为其整数表示；`chr()` 函数则把整数码点转换为含有对应字符的字符串。

```python
>>> ord('牛')
29275
>>> chr(29275)
'牛'
```

### 2.2 Unicode 编码

Unicode 标准定义了字符到码点（整数）的映射，但直接在 Unicode 码点上训练分词器并不现实：词表会大到不可接受（约 15 万个条目），而且稀疏（许多字符相当罕见）。因此，我们改用一种 **Unicode 编码**，它把 Unicode 字符转换为字节序列。Unicode 标准本身定义了三种编码：UTF-8、UTF-16 与 UTF-32，其中 UTF-8 是互联网上的主导编码（超过 98% 的网页）。

要把 Unicode 字符串编码为 UTF-8，我们可以用 Python 的 `encode()` 函数。要访问 Python `bytes` 对象底层的字节值，我们可以迭代它（例如调用 `list()`）。最后，我们可以用 `decode()` 函数把 UTF-8 字节串解码为 Unicode 字符串。

```python
>>> test_string = "hello! こんにちは!"
>>> utf8_encoded = test_string.encode("utf-8")
>>> print(utf8_encoded)
b'hello! \xe3\x81\x93\xe3\x82\x93\xe3\x81\xab\xe3\x81\xa1\xe3\x81\xaf!'
>>> print(type(utf8_encoded))
<class 'bytes'>
>>> # 获取编码后字符串的字节值（0 到 255 的整数）。
>>> list(utf8_encoded)
[104, 101, 108, 108, 111, 33, 32, 227, 129, 147, 227, 130, 147, 227, 129, 171, 227, 129,
161, 227, 129, 175, 33]
>>> # 一个字节并不一定对应一个 Unicode 字符！
>>> print(len(test_string))
13
>>> print(len(utf8_encoded))
23
>>> print(utf8_encoded.decode("utf-8"))
hello! こんにちは!
```

把 Unicode 码点转换为字节序列（例如通过 UTF-8 编码），本质上就是把一个码点序列（21 位整数、159,801 个有效值）转换成字节值序列（0 到 255 的整数）。长度为 256 的字节词表处理起来容易得多。使用字节级分词时，我们无需担心词表外（out-of-vocabulary）token，因为我们知道任何输入文本都可以表示为 0 到 255 的整数序列。

### 2.3 子词分词

字节级分词可以缓解词级分词器面临的词表外问题，但把文本切成字节会产生极长的输入序列。这会拖慢模型训练：一个 10 词的句子在词级语言模型中可能只有 10 个 token，在字符级模型中却可能有 50 个甚至更多 token（取决于单词长度）。处理这些更长的序列意味着模型每一步都要做更多计算。此外，在字节序列上做语言建模本身也更困难，因为更长的输入序列在数据中制造了长距离依赖。

**子词分词**介于词级分词器与字节级分词器之间。注意字节级分词器的词表有 256 个条目（字节值为 0 到 255）。子词分词器以更大的词表为代价，换取对输入字节序列更好的压缩。例如，如果字节序列 `b'the'` 在我们的原始文本训练数据中频繁出现，为它分配一个词表条目就能把这个 3-token 序列压缩成单个 token。

那么，如何挑选要加入词表的子词单元？R. Sennrich et al. [3] 提出使用**字节对编码**（BPE；P. Gage [5]），这是一种压缩算法：它迭代地把最频繁的字节对替换（"合并"）为一个新的、未使用过的索引。注意该算法通过向词表添加子词 token 来**最大化**输入序列的压缩率——如果某个词在输入文本中出现次数足够多，它就会被表示为单个子词单元。

用 BPE 构建词表的子词分词器通常被称为 **BPE 分词器**。在本作业中，我们将实现字节级 BPE 分词器，其词表条目是字节或合并后的字节序列，这使我们在"词表外处理"与"可控的输入序列长度"两方面兼得。构建 BPE 分词器词表的过程被称为对该分词器进行"训练"。

### 2.4 BPE 分词器训练

BPE 分词器的训练流程由三个主要步骤组成。

#### 词表初始化

分词器词表是一个从字节串 token 到整数 ID 的一一映射。由于我们训练的是字节级 BPE 分词器，初始词表就是全体字节的集合。字节值共有 256 种可能，因此初始词表大小为 256。

#### 预分词（Pre-tokenization）

有了词表之后，你原则上可以统计文本中相邻字节共同出现的频次，并从最高频的字节对开始合并。但这在计算上相当昂贵，因为每做一次合并都要把语料完整遍历一遍。此外，直接在整份语料上跨字符合并，可能得到只在标点上不同的 token（例如 `dog!` 与 `dog.`）。这类 token 会拿到完全不同的 token ID，尽管它们很可能语义高度相近（仅差一个标点）。

为避免这一点，我们先对语料做**预分词**。你可以把它看成一种面向整份语料的粗粒度分词，用来帮助我们统计字符对出现的频次。例如，单词 `'text'` 可能是一个出现 10 次的预分词；这样在统计字符 't' 与 'e' 相邻出现的频次时，我们就能看出单词 'text' 中有 't' 与 'e' 相邻，从而把它们的计数直接加 10，而不必再去遍历语料。由于我们训练的是字节级 BPE 模型，每个预分词都表示为一个 UTF-8 字节序列。

R. Sennrich et al. [3] 的原始 BPE 实现就是简单地按空白切分来做预分词（即 `s.split(" ")`）。这种做法在基于 SentencePiece 的分词器中仍可见到（例如 Llama 1 和 Llama 2 的分词器）。

大多数现代分词器使用基于正则的预分词器，这一做法源自 GPT-2（A. Radford et al. [6]）。我们将使用原始正则的一个更美观的版本，取自 `github.com/openai/tiktoken/pull/234/files`：

```python
>>> PAT = r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""
```

用这个预分词器交互式地切一些文本，有助于体会它的行为：

```python
>>> # 需要 `regex` 包
>>> import regex as re
>>> re.findall(PAT, "some text that i'll pre-tokenize")
['some', ' text', ' that', ' i', "'ll", ' pre', '-', 'tokenize']
```

不过在代码中使用它时，你应当用 `re.finditer`，这样在构造"预分词 → 计数"的映射时就不必把所有预分词都存下来。

#### 计算 BPE 合并

现在我们已经把输入文本转成预分词、并把每个预分词表示成 UTF-8 字节序列，可以计算 BPE 合并了（也就是训练 BPE 分词器）。从高层看，BPE 算法迭代地统计每一对字节，找出频次最高的那一对（"A"、"B"），然后把该最频繁对（"A"、"B"）的每一处出现都合并，也就是替换为新 token "AB"。这个新合并出的 token 被加入词表；因此 BPE 训练结束后的词表大小等于初始词表大小（本作业中为 256）加上训练期间执行的 BPE 合并次数。为了训练效率，我们不统计跨越预分词边界的字节对²。在计算合并时，若字节对频次并列，则以确定性的方式改为优先选择**字典序更大**的那一对。例如，若 ("A", "B")、("A", "C")、("B", "ZZ")、("BA", "A") 这四对的频次并列最高，我们会合并 ("BA", "A")：

```python
>>> max([("A", "B"), ("A", "C"), ("B", "ZZ"), ("BA", "A")])
('BA', 'A')
```

> ² 注意，R. Sennrich et al. [3] 的原始 BPE 表述规定要包含一个词尾（end-of-word）token。训练字节级 BPE 模型时我们不添加词尾 token，因为所有字节（包括空白与标点）都已包含在模型词表中。既然我们显式地表示空格与标点，学到的 BPE 合并自然会反映这些词边界。

#### 特殊 token

通常，某些字符串（例如 `<|endoftext|>`）被用来编码元数据（例如文档之间的边界）。编码文本时，常常希望把某些字符串当作"特殊 token"，它们**永远不应被拆成多个 token**（即始终保留为单个 token）。例如，序列结束字符串 `<|endoftext|>` 应始终保留为单个 token（即单个整数 ID），这样我们才知道何时停止从语言模型生成。这些特殊 token 必须加入词表，从而拥有对应且固定的 token ID。

R. Sennrich et al. [3] 的算法 1 给出了一个低效的 BPE 分词器训练实现（基本上就是上面列出的步骤）。作为第一个练习，实现并测试该函数来检验你的理解，可能会有帮助。

> **示例（bpe_example）：BPE 训练示例**
>
> 下面是取自 R. Sennrich et al. [3] 的一个风格化示例。考虑由以下文本构成的语料
>
> ```
> low low low low low
> lower lower widest widest widest
> newest newest newest newest newest newest
> ```
>
> 并设词表中含有一个特殊 token `<|endoftext|>`。
>
> **词表**
>
> 我们用特殊 token `<|endoftext|>` 与 256 个字节值初始化词表。
>
> **预分词**
>
> 为简化并聚焦于合并过程，本示例假设预分词就是按空白切分。预分词并计数后，得到如下频次表：
>
> ```
> {low: 5, lower: 2, widest: 3, newest: 6}
> ```
>
> 用 `dict[tuple[bytes, ...], int]` 来表示比较方便，例如 `{(l,o,w): 5, …}`。注意在 Python 中，即使单个字节也是 `bytes` 对象。Python 没有表示单个字节的 `byte` 类型，正如它没有表示单个字符的 `char` 类型。
>
> **合并**
>
> 我们首先考察每一对相邻字节，把出现该对的单词的频次累加起来：`{lo: 7, ow: 7, we: 8, er: 2, wi: 3, id: 3, de: 3, es: 9, st: 9, ne: 6, ew: 6}`。('e', 's') 与 ('s', 't') 频次并列，因此取字典序更大的那一对，即 ('s', 't')。随后我们合并各预分词，得到 `{(l,o,w): 5, (l,o,w,e,r): 2, (w,i,d,e,st): 3, (n,e,w,e,st): 6}`。
>
> 第二轮中可见 (e, st) 是最常见的对（计数为 9），合并后得到 `{(l,o,w): 5, (l,o,w,e,r): 2, (w,i,d,est): 3, (n,e,w,est): 6}`。如此继续，最终得到的合并序列为 `['s t', 'e st', 'o w', 'l ow', 'w est', 'n e', 'ne west', 'w i', 'wi d', 'wid est', 'low e', 'lowe r']`。
>
> 若只取前 6 次合并，我们得到 `['s t', 'e st', 'o w', 'l ow', 'w est', 'n e']`，词表元素则为 `[<|endoftext|>, [...256 BYTE CHARS], st, est, ow, low, west, ne]`。
>
> 用这个词表与这组合并，单词 `newest` 会被分词为 `[ne, west]`。

### 2.5 在 BPE 分词器训练上做实验

#### 并行化预分词

你会发现一个主要瓶颈是预分词步骤。你可以借助内置的 `multiprocessing` 库把代码并行化，从而加速预分词。具体而言，我们建议在预分词的并行实现中把语料分块，并确保**分块边界落在某个特殊 token 的起始处**。你可以原样使用以下链接中的起始代码来获得分块边界，然后据此把工作分配到各进程：

`https://github.com/stanford-cs336/assignment1-basics/blob/main/cs336_basics/pretokenization_example.py`

这种分块方式始终是合法的，因为我们从不希望跨文档边界合并。就本作业而言，你完全可以一律这样切分。不必担心"收到一份不含 `<|endoftext|>` 的超大语料"这种边界情况。

#### 预分词之前移除特殊 token

在用正则模式（通过 `re.finditer`）运行预分词之前，你应当把语料（若采用并行实现，则是你负责的分块）中的所有特殊 token 剥离出去。务必**按特殊 token 切分**，这样它们所界定的文本之间不会发生任何合并。例如，若你的语料（或分块）形如 `[Doc 1]<|endoftext|>[Doc 2]`，你应当按特殊 token `<|endoftext|>` 切分，分别对 `[Doc 1]` 与 `[Doc 2]` 做预分词，从而不会有任何合并跨越文档边界。换言之，特殊 token 在训练期间定义**硬切分边界**，但它们本身不应计入合并统计。这可以用 `re.split` 完成，以 `"|".join(special_tokens)` 作为分隔符（注意妥善使用 `re.escape`，因为特殊 token 中可能出现 `|`）。测试 `test_train_bpe_special_tokens` 会检验这一点。

#### 优化合并步骤

上面风格化示例中的朴素 BPE 训练实现之所以慢，是因为每一次合并都要遍历全部字节对来找出最频繁的那一对。然而，每次合并之后**唯一会变的对计数，只有与被合并那一对重叠的那些**。因此，可以通过为所有对的计数建立索引、并对这些计数做增量更新来提升 BPE 训练速度，而不是显式遍历每一对字节去统计频次。借助这种缓存做法你能获得可观的加速；不过要说明，BPE 训练中的合并部分在 Python 里无法并行化。

> 你应当使用 `cProfile` 或 `py-spy` 之类的剖析工具找出实现中的瓶颈，并集中优化这些地方。

> **低资源提示："降规模"（Downscaling）**
> 与其一上来就在完整的 TinyStories 数据集上训练分词器，我们建议你先在一小部分数据上训练，即所谓"调试数据集"。例如，你可以改在 TinyStories 验证集上训练分词器，它是 22K 个文档而不是 2.12M 个。这体现了一条通用策略：尽可能降规模以加速开发——例如使用更小的数据集、更小的模型规模等。为调试数据集或超参数配置选定规模需要仔细权衡：你希望调试集大到足以暴露与完整配置相同的瓶颈（这样你所做的优化才能推广过去），但又不能大到跑起来没完没了。

### 2.6 BPE 分词器：编码与解码

在作业的上一部分，我们实现了一个在输入文本上训练 BPE 分词器的函数，从而得到分词器词表与 BPE 合并列表。现在，我们将实现一个 BPE 分词器：它加载给定的词表与合并列表，并用二者在文本与 token ID 之间做编码与解码。

#### 2.6.1 编码文本

用 BPE 编码文本的过程，与训练 BPE 词表的过程如出一辙，主要有几个步骤。

**第 1 步：预分词。** 首先对序列做预分词，并把每个预分词表示为 UTF-8 字节序列，与 BPE 训练时相同。我们将把这些字节在**每个预分词内部**合并为词表元素，各预分词独立处理（不跨越预分词边界合并）。

**第 2 步：应用合并。** 接着，我们取 BPE 训练期间产生的词表元素合并序列，按相同的创建顺序将其应用到各个预分词上。

> **示例（bpe_encoding）：BPE 编码示例**
>
> 例如，设输入字符串为 `'the cat ate'`，词表为 `{0: b' ', 1: b'a', 2: b'c', 3: b'e', 4: b'h', 5: b't', 6: b'th', 7: b' c', 8: b' a', 9: b'the', 10: b' at'}`，学到的合并为 `[(b't', b'h'), (b' ', b'c'), (b' ', b'a'), (b'th', b'e'), (b' a', b't')]`。
>
> 首先，预分词器会把该字符串切分为 `['the', ' cat', ' ate']`。然后我们逐个预分词应用 BPE 合并。
>
> 第一个预分词 `'the'` 初始表示为 `[b't', b'h', b'e']`。查看合并列表，可用的第一个合并是 `(b't', b'h')`，用它把该预分词变成 `[b'th', b'e']`。然后回到合并列表，下一个可用的合并是 `(b'th', b'e')`，据此把预分词变成 `[b'the']`。最后再看合并列表，已没有可用的合并（因为整个预分词已合并为单个 token），于是应用 BPE 合并的过程结束。对应的整数序列为 `[9]`。
>
> 对其余预分词重复该过程：预分词 `' cat'` 应用 BPE 合并后表示为 `[b' c', b'a', b't']`，对应整数序列 `[7, 1, 5]`；最后一个预分词 `' ate'` 应用 BPE 合并后为 `[b' at', b'e']`，对应整数序列 `[10, 3]`。因此，输入字符串编码的最终结果是 `[9, 7, 1, 5, 10, 3]`。

**特殊 token**

在编码文本时，你的分词器应能正确处理用户定义的特殊 token（在构造分词器时提供）。

**内存考量**

假设我们要分词一个大到无法装入内存的文本文件。为了高效地分词这个大文件（或任何其他数据流），我们需要把它拆分成可管理的块，逐块处理，使内存复杂度为常数，而不是随文本规模线性增长。在此过程中，必须确保**没有 token 跨越块边界**，否则得到的分词结果就会不同于"把整个序列一次读入内存"的朴素做法。

#### 2.6.2 解码文本

要把整数 token ID 序列解码回原始文本，我们只需在词表中查得每个 ID 对应的条目（一个字节序列），把它们拼接起来，再把字节解码为 Unicode 字符串。注意输入的 ID 并不保证能映射为合法的 Unicode 字符串（因为用户可以输入任意整数 ID 序列）。当输入的 token ID 无法产生合法 Unicode 字符串时，你应当把畸形字节替换为官方 Unicode 替换字符 U+FFFD³。`bytes.decode` 的 `errors` 参数控制 Unicode 解码错误的处理方式，使用 `errors='replace'` 会自动把畸形数据替换为替换标记。

> ³ 关于 Unicode 替换字符的更多信息，见 en.wikipedia.org/wiki/Specials_(Unicode_block)#Replacement_character。

**问题（tokenizer）：实现分词器（15 分）**

**交付物：** 实现一个 `Tokenizer` 类：给定词表与合并列表，把文本编码为整数 ID，并把整数 ID 解码为文本。你的分词器还应支持用户提供的特殊 token（若它们尚不在词表中，则追加进去）。我们推荐以下接口：

- `def __init__(self, vocab, merges, special_tokens=None)` — 由给定的词表、合并列表以及（可选的）特殊 token 列表构造分词器。该函数应接受以下参数：
  - `vocab: dict[int, bytes]`
  - `merges: list[tuple[bytes, bytes]]`
  - `special_tokens: list[str] | None = None`
- `def from_files(cls, vocab_filepath, merges_filepath, special_tokens=None)` — 类方法：由序列化的词表与合并列表（格式与你的 BPE 训练代码输出相同）以及（可选的）特殊 token 列表构造并返回一个 `Tokenizer`。该方法应接受以下额外参数：
  - `vocab_filepath: str`
  - `merges_filepath: str`
  - `special_tokens: list[str] | None = None`
- `def encode(self, text: str) -> list[int]` — 把输入文本编码为 token ID 序列。
- `def encode_iterable(self, iterable: Iterable[str]) -> Iterator[int]` — 给定一个字符串可迭代对象（例如 Python 文件句柄），返回一个惰性产出 token ID 的生成器。对于无法直接读入内存的大文件，这是实现内存高效分词的必要条件。
- `def decode(self, ids: list[int]) -> str` — 把 token ID 序列解码为文本。

要用我们提供的测试检验你的 `Tokenizer`，你首先需要实现 `[adapters.get_tokenizer]` 处的测试适配器，然后运行 `uv run pytest tests/test_tokenizer.py`。你的实现应当能通过全部测试。
